# Clinic Management System 🏥

نظام شامل ومتقدم لإدارة العيادات الطبية. تم تصميم هذا المشروع ليكون تطبيقاً عملياً للمفاهيم الهندسية المتقدمة في تطوير البرمجيات، مع التركيز على الأداء العالي، الأمان، وقابلية التوسع والصيانة. ينقسم المشروع إلى واجهة خلفية (Backend) مبنية بـ .NET، وواجهة أمامية (Frontend) حديثة مبنية بـ Angular.

---

## 🏗️ البنية المعمارية للواجهة الخلفية (Backend Architecture)

تم تقسيم الواجهة الخلفية بناءً على مبدأ **Clean Architecture** (البنية النظيفة). يضمن هذا التقسيم عدم تداخل المسؤوليات (Separation of Concerns)، مما يسهل اختبار الكود وتطويره مستقبلاً دون أن تؤثر التغييرات في مكان ما على باقي أجزاء النظام.

النظام مقسم إلى 4 طبقات رئيسية:
1. **طبقة المجال (Domain Layer):**
   - تحتوي على الكيانات الأساسية للمشروع (Entities) مثل `Doctor`, `Patient`, `Appointment`, و `Employee`.
   - لا تعتمد على أي طبقة أخرى، وهي جوهر النظام.
2. **طبقة التطبيق (Application Layer):**
   - تحتوي على منطق الأعمال (Business Logic) وتطبيق نمط **CQRS** (فصل الأوامر عن الاستعلامات).
   - تستخدم واجهات (Interfaces) للتواصل مع قاعدة البيانات والخدمات الخارجية دون معرفة تفاصيل تنفيذها.
3. **طبقة البنية التحتية (Infrastructure Layer):**
   - مسؤولة عن التنفيذ الفعلي للواجهات، مثل التعامل مع قاعدة البيانات (Entity Framework Core)، إرسال الإيميلات، والتعامل مع نظام الملفات.
4. **طبقة العرض (Presentation Layer - Web API):**
   - هي الواجهة التي تستقبل طلبات الـ HTTP من المستخدم (أو الـ Frontend).
   - تحتوي على الـ Controllers التي تقوم فقط بتوجيه الطلبات إلى طبقة الـ Application باستخدام `MediatR` ولا تحتوي على أي منطق أعمال مباشر.

## ⚡ كيف تم تطبيق CQRS و MediatR وما الفائدة؟

في المشاريع التقليدية، يتم وضع كل الكود في الـ Controllers أو Services، مما يجعلها ضخمة وبطيئة وصعبة الصيانة. هنا، استخدمنا نمط **CQRS** عبر مكتبة **MediatR**:

- **الاستعلامات (Queries):** مخصصة فقط لقراءة البيانات (مثال: `GetAllDoctorsQuery` أو `GetAppointmentsQuery`). لا تقوم بتعديل أي شيء في قاعدة البيانات، ويتم تحسينها باستخدام `AsNoTracking()` لتوفير استهلاك الذاكرة وتخفيف العبء على الـ Server، مما يجعل جلب البيانات سريعاً جداً.
- **الأوامر (Commands):** مخصصة فقط لتعديل البيانات (إضافة، تعديل، حذف) (مثال: `RegisterEmployeeCommand` أو `CreateAppointmentCommand`). تركز فقط على تنفيذ قواعد الأعمال المعقدة قبل حفظها.

**فائدة هذه الطريقة (Decoupling):** الـ Controller لا يعرف كيف يتم حفظ الموظف، هو فقط يستقبل الطلب ويرسل أمر `RegisterEmployeeCommand` عبر `MediatR` ليتعامل معه كلاس آخر. هذا يفك الارتباط تماماً بين الـ Controller ومنطق التنفيذ الفعلي، ويسمح لكل عملية بالعمل بشكل مستقل مما يحقق مبدأ الـ Single Responsibility.

## 🛡️ أبرز ميزات ومكونات .NET المستخدمة في المشروع

تم استغلال أقوى وأحدث ميزات إطار عمل **.NET Core** لبناء نظام آمن ومستقر:

1. **حقن التبعية (Dependency Injection - DI):**
   - تم استخدام الـ DI المدمج في .NET بشكل كامل لربط الطبقات ببعضها عبر (Interfaces)، مما يجعل النظام قابلاً لاختبار الوحدات (Unit Testing) بسهولة ويقلل استهلاك الذاكرة عن طريق التحكم في دورة حياة الكائنات (Scoped, Transient, Singleton).

2. **التحقق المسبق عبر مسار المعالجة (Validation Pipeline Behavior):**
   - استخدمنا مكتبة **FluentValidation** وقمنا بربطها في مسار **MediatR Pipeline Behaviors**. هذا يعني أن أي طلب قادم من المستخدم يتم فحصه تلقائياً في الخلفية (كـ Middleware بين الـ Controller والـ Command) قبل أن يصل إلى الكود الخاص بك أو الـ Database. إذا كان هناك خطأ في البيانات (مثلاً إيميل غير صحيح)، يتم قطع الاتصال فوراً وإرجاع خطأ `400 Bad Request`، مما يوفر طاقة المعالجة (CPU/RAM).

3. **معالجة الأخطاء المركزية (Global Exception Handling Middleware):**
   - بدلاً من استخدام `try/catch` في كل Controller وتكرار الكود، تم بناء `ExceptionHandlingMiddleware` مخصص يلتقط أي خطأ (Exception) يحدث في أي مكان في النظام ويقوم بتنسيقه وإرساله للواجهة الأمامية كرسالة JSON احترافية (مثل أخطاء الـ Validation)، مع ضمان إرسال ترويسات (CORS) بشكل صحيح لتستطيع الواجهة قراءته.

4. **نظام المصادقة والصلاحيات المتقدم (Identity & JWT):**
   - تم دمج **ASP.NET Core Identity** لإدارة المستخدمين (تشفير كلمات المرور، الحماية).
   - الاعتماد على **JWT (JSON Web Tokens)** لتسجيل الدخول بدلاً من الـ Sessions التقليدية، مما يجعل الـ API بدون حالة (Stateless) وجاهزاً للعمل على أكثر من سيرفر في نفس الوقت.

5. **اعتراض العمليات في قاعدة البيانات (EF Core Interceptors):**
   - استخدمنا `AuditableEntitySaveChangesInterceptor` لملء حقول التتبع تلقائياً (Auditing) مثل `CreatedAt` و `LastModifiedAt` في أي وقت يتم فيه إضافة أو تعديل في قاعدة البيانات، مما يضمن دقة السجلات دون الحاجة لكتابة هذا الكود يدوياً في كل Endpoint.

## 💻 الواجهة الأمامية (Frontend)
- **الإطار العام:** Angular 22 (Standalone Components).
- **مكتبة المكونات (UI):** PrimeNG لتوفير مكونات واجهة جاهزة واحترافية.
- **التنسيق:** Tailwind CSS، وتم دمجها بعناية مع PrimeNG عبر ملفات الـ SCSS لمنع أي تعارض في التنسيقات (مثل توسيط النوافذ المنبثقة)، للحصول على واجهة سريعة التجاوب.
- **إدارة الأخطاء:** تم إنشاء `error.interceptor` لالتقاط أخطاء السيرفر (مثل 400 و 401) وعرض رسائل تنبيهية (Toasts) للمستخدم. و `jwt.interceptor` لإرفاق الـ Token تلقائياً مع كل طلب.

## ⚙️ كيفية تشغيل المشروع محلياً

### متطلبات التشغيل:
- .NET SDK (الإصدار الأخير).
- Node.js & npm.
- SQL Server.
- Angular CLI.

### 1. تشغيل الباك إند:
1. افتح موجه الأوامر في `src/Presentation/ClinicManagement.WebApi`.
2. حدّث قاعدة البيانات:
   ```bash
   dotnet ef database update --project ../../Infrastructure/ClinicManagement.Infrastructure --startup-project .
   ```
3. شغل السيرفر:
   ```bash
   dotnet run
   ```

### 2. تشغيل الفرونت إند:
1. افتح مسار `src/clinic-management-frontend`.
2. ثبّت الحزم:
   ```bash
   npm install
   ```
3. شغل المشروع:
   ```bash
   ng serve
   ```
4. المتصفح: `http://localhost:4200`.
